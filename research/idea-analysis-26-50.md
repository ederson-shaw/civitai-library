# idea analysis 26-50 (filters + search range)

analyst: ideas 26-50. source: research/codex-design-ideas.md §3. laws applied: REQUIREMENTS.md (fewer clicks, results visible, fast import, format/order matter, best-per-category instantly understandable) + CRITERIA.md (data honesty, manual vram, per-lane nsfw normalization).

**shared assumptions (apply to every idea below):**
- data: `entries.json` generated by python build step (garimpo pull + curation merge). runtime = vanilla JS over in-memory array, zero server.
- pullable from API: `type`, `baseModels`, stats (all-time, `{value, window, pulled_at}`), `nsfwLevel`, creator username, version `updatedAt`. NOT pullable: vram, inputs, outputs, locks, duration, audio role → curator fields (CRITERIA.md already rules vram manual).
- one controlled-vocabulary const (`vocab.js`, build-checked) feeds hardware labels, GPU presets, output filters, intent chips, synonym table — single source, no drift.
- constraint note: task law = nsfw previews ALLOWED, blurred until toggle, SFW default. this overrides codex doc §5's stricter "no explicit imagery ever" line; blur mechanics from §5 still apply.

---

### 26 — hardware context labels
**restatement:** GB figures translated into machine classes people recognize — `8 GB laptop`, `12 GB desktop`, `Cloud recommended` — not bare numbers.
**mechanism:** build step maps curated `entry.vram` → one of ≤6 labels via the shared vocab const; bakes `<span class="hw" data-vram="8">8 GB laptop</span>` into card header next to title (with #25). no runtime logic — pure build-time render. CSS: fits-rig = neutral chip, exceeds = coral tint when a rig is selected (#33).
**simulation:** kenji, burned twice downloading a checkpoint that swapped his 8 GB MacBook into a slideshow, scans the persona grid. Every card says `8 GB laptop` or `12 GB desktop` where he expects jargon. He filters nothing, reads nothing technical, and already knows which half of the grid is his. Relief — "someone finally speaks my machine's language."
**micro-criteria:** (1) 100% of entries carry exactly one hardware label — build asserts no null vram; (2) ≤6 labels, identical strings sitewide (never `8GB` in one place, `8 GB laptop` in another — grep test in build); (3) label vocabulary === GPU preset vocabulary (#33), one const.
**cost:** trivial. one mapping table, edited once per GPU generation.
**verdict:** ADOPT 9 — "instantly understandable" made literal; translates spec into the shopper's own hardware vocabulary at zero runtime cost.

### 27 — entry type pill (LoRA / checkpoint / workflow / voice / utility)
**restatement:** a type glyph+word pill on every card and list row — the first question ("what even is this?") answered before any other reading.
**mechanism:** `entry.type` from API (models) or curation (workflows) → colored pill baked at build into card, detail header, compare rows, and palette/search results. text+icon, aria-label. ≤5 values, build fails on unknown type.
**simulation:** kenji half-remembers a YouTube tutorial about "dragging workflows into ComfyUI". On the grid he sees `WORKFLOW` pills vs `LORA` pills; he clicks a workflow card because that word matches his tutorial. Without the pill he'd be guessing which of forty similar-looking image cards does what.
**micro-criteria:** (1) build asserts type on 100% of entries — a null type fails CI; (2) same pill component in card, detail, compare (grep test: one class name, not three variants); (3) ≤5 types; "utility" exists so nothing lands in "other".
**cost:** trivial. data exists for models; workflows are authored by us.
**verdict:** ADOPT 9 — cheapest possible orientation layer; invisible when present, disorienting when absent.

### 28 — compatible base model beside the type
**restatement:** base family rendered as one fact with the type pill — `LoRA · Flux.1 D` — because type-without-base answers half the question.
**mechanism:** build concatenates `type` + `baseModels[0]` into the card header meta line; multi-base entries render `Flux / SDXL` (all listed, never "various"). same string feeds `data-base` attr consumed by #34 filter.
**simulation:** marcus built his whole persona pipeline on Flux. last month a slick-looking LoRA turned out to be SDXL-only and cost him an evening. here the mistake dies pre-click: every card's second line says `LoRA · SDXL` or `LoRA · Flux.1 D`. he does his two-second compatibility ritual without opening a single detail page.
**micro-criteria:** (1) base visible on card without hover or expand (in first 2 lines); (2) multi-base entries list every base — no truncation to first + "…"; (3) card strings === #34 chip strings, verified by build-time set comparison.
**cost:** trivial. `baseModels` straight from API.
**verdict:** ADOPT 9 — the two facts every buyer checks first, fused into one glance; format/order law.

### 29 — community stats as dated signals
**restatement:** downloads/likes shown with pull-date and framed as crowd signal, visually subordinate to our editorial score — never confused, never faked-fresh.
**mechanism:** build renders stats row in mono metadata font: `127k downloads · 79k likes · pulled 2026-08-30`, from CRITERIA' `{value, window:"all-time", pulled_at}` snapshot. delta arrow only when ≥2 snapshots exist; single-snapshot entries render "no history yet". tooltip: "all-time counts from the civitai API — not our score."
**simulation:** the owner opens a detail page and sees `8.9` big + editorial verdict, and below it the small dated crowd line. he doesn't have to ask (again) which number is ours. he checks three more cards — same separation everywhere — and stops worrying that we're dressing civitai counts up as curation.
**micro-criteria:** (1) 100% of stat rows carry a visible pulled date; (2) editorial score is visually dominant (≥2× size, distinct color) — a screenshot test at build proves no card renders them at equal weight; (3) <2 snapshots ⇒ literal string "no history yet", never a trend arrow.
**cost:** low. build-time render; snapshot store grows with each pull (rank-keeper already planned).
**verdict:** ADOPT 8 — CRITERIA data-honesty rules made visible; trust infrastructure for ~zero runtime cost.

### 30 — `Open original on Civitai` always visible
**restatement:** persistent, verbatim-labeled outbound link on every detail page (and a quiet version on cards) — the provenance contract with both civitai and the user.
**mechanism:** build bakes `<a href="https://civitai.com/models/{sourceId}" target="_blank" rel="noopener">Open original on Civitai</a>` into the detail header AND the fixed proof rail (Direction B borrow). never hover-only; opens new tab so the user's lane/filters survive.
**simulation:** lia, in the mature lane, wants the full original gallery before committing disk space. the link sits top-right, new tab, her place in our site untouched. she comes back and imports. the site behaved like a guide with an exit, not a cage — that's why she'll use it again tomorrow.
**micro-criteria:** (1) build asserts link on 100% of detail pages (CI grep); (2) exact string "Open original on Civitai" + `target=_blank` + `rel=noopener` (mature-gating doc requires the label); (3) visible without scrolling at ≥1024px.
**cost:** trivial.
**verdict:** ADOPT 10 — REQUIREMENTS verbatim ("link back to civitai original on every entry"); non-negotiable, free.

### 31 — four-filter bar discipline
**restatement:** the filter bar shows exactly FOUR filter groups by default (VRAM, base model, output/task, freshness); everything else hides behind one `+ more` toggle.
**mechanism:** static `<fieldset>` with 4 primary chip groups in fixed DOM/tab order; remaining groups live in a `<details>` "More filters". JS toggles `aria-pressed`, recomputes visible set from in-memory array, re-renders grid via DocumentFragment, count announced in `aria-live`. which four is a build constant — changing it is a deliberate edit, not drift.
**simulation:** kenji comes from civitai's twelve-filter advanced search where he froze. here: four chips he actually understands. he taps `8 GB`, the grid halves, one `output` tap later he's looking at three relevant cards. no scroll of filter soup, no "sort by" paradox. it felt like a human sorted the internet down for him.
**micro-criteria:** (1) exactly 4 visible groups by default — build counts DOM and fails if 5+; (2) any hidden filter reachable in ≤2 clicks (open details → tap chip); (3) bar occupies one row at ≥768px with no wrap-jump when chips toggle.
**cost:** trivial code; the real cost is the DECISION (which four) + discipline keeping it four as ideas accrete. the four chosen: VRAM (#32), base (#34), output (#36), freshness (#49) — each maps to a law below.
**verdict:** ADOPT 9 — "fewer clicks, instantly understandable" starts at the bar; this is the container law for ideas 32-39 (they define the set, this defines the frame).

### 32 — VRAM as first filter
**restatement:** VRAM occupies slot 1 (leftmost = first tab = first read) because it's the only filter that makes options IMPOSSIBLE rather than unpreferred.
**mechanism:** build renders the VRAM group first in DOM order; selection filters `entry.vram <= selected` (or cloud), non-matching cards leave the grid entirely (not dimmed — gone, per "eliminate impossible options"). takes effect in-memory, ≤50ms, no fetch.
**simulation:** marcus has three free minutes and a 12 GB card. the first control his eye lands on is VRAM; one tap on `12 GB` and the grid is only things he can actually run tonight. he never once wonders "will this even load" — the site asked his constraint before offering opinions.
**micro-criteria:** (1) VRAM group is first in DOM and first in tab order (build asserts index 0); (2) works only if 100% of entries carry vram (CRITERIA: manual badge — build assert, missing badge = CI fail, because a filter that ignores un-badged entries lies); (3) effect visible ≤50ms after click.
**cost:** runtime trivial; real cost = curating vram badges per entry (one-time + per new entry). CRITERIA already mandates the badge, so the filter is free on top.
**verdict:** ADOPT 9 — impossibility-elimination is the sharpest possible first cut; hardware-first matches owner's stated affections (z-image/turbo-class awareness).

### 33 — GPU presets (6 / 8 / 12 / 16+ / Cloud)
**restatement:** five fixed bucket chips instead of a slider or number input — the chip IS the user's machine.
**mechanism:** `GPU_PRESETS = [6, 8, 12, 16, 'cloud']` in the shared vocab const (same source as #26 labels). semantics "runs on my X GB": `entry.vram <= preset`, cloud preset shows all + highlights cloud-recommended. single-select group; tooltip states the semantics in plain words.
**simulation:** kenji doesn't know what his 8 GB "means" for generation. there's no slider to fiddle, no min/max mental math — a chip literally says `8 GB`. one tap, correct answer. the interface assumed his knowledge level exactly.
**micro-criteria:** (1) exactly 5 presets, ≤3 words each; (2) tooltip copy "shows entries that run on X" (no ambiguity between "needs exactly" vs "runs on"); (3) preset label strings ⊆ #26 label vocabulary — build set-check.
**cost:** trivial.
**verdict:** ADOPT 9, implementation MERGED with #26 — one shared const drives both; preset>slider for a curated set of ~hundreds.

### 34 — base model family filter
**restatement:** chips for each base family present in the dataset (Flux / SDXL / Z-Image / video bases…) because stacks don't mix bases and users arrive already owning one.
**mechanism:** chip list auto-generated at build from `distinct(baseModels)` — never a hand-maintained list that goes stale. multi-select, OR within the group, AND against other groups. matching via `data-base` baked per card.
**simulation:** marcus taps `Flux` and the grid becomes only composable pieces for his pipeline. he wasn't reading base strings card-by-card (even though #28 shows them) — he wanted the pre-cut view, and one chip gave it.
**micro-criteria:** (1) chips === distinct bases in dataset at build time (auto, zero manual list); (2) multi-select OR within group, cross-group AND — property test at build over random combos; (3) empty-match chips render disabled with count 0 (see NEW idea N1), never clickable dead-ends.
**cost:** trivial.
**verdict:** ADOPT 8 — obvious and nearly free; ranked under VRAM because base is already visible per-card (#28) and the set is small — it's convenience, not elimination.

### 35 — input-type filter (text / image / pose / reference face / audio / video)
**restatement:** filter by what you FEED the entry — separates "I have a photo of her" from "I only have words".
**mechanism:** NEW curated field `entry.inputs[]` (curation schema addition — API has no such field). multi-select chips match on any overlap. vocabulary ≤6 values from the shared const. build prints a coverage report (inputs populated %) per lane instead of hard-failing.
**simulation:** lia has reference photos of herself and wants entries that accept one. she taps `reference face` and gets the identity-lock LoRAs plus the face-reference workflows, skipping everything text-only. one chip replaced twenty card-openings — the filter speaks her situation, not the tech's taxonomy.
**micro-criteria:** (1) inputs on 100% of workflows and ≥80% of models, gaps listed in build report (curator queue, not silent); (2) ≤6 controlled values, no free tags; (3) zero-match chip disabled with live count (N1) — never a dead click.
**cost:** MEDIUM — the runtime is trivial; the cost is a new manual metadata axis × every entry. this is a curation-tax decision, not a code decision.
**verdict:** ADOPT 7 — high decision value for persona/mature lanes (reference-face is a real lane-C job), but it only pays if the curation budget exists; without coverage it degrades into an empty filter. guarded adopt with build-time coverage report.

### 36 — output-type filter (portrait / product still / talking head / reel / voice clip)
**restatement:** filter by what you GET — the "enter through I need a result, not a LoRA" principle (#5) turned into a control.
**mechanism:** curated `entry.outputs[]`; chips share ONE vocabulary const with #42 intent chips and lane copy (build asserts the sets match). selecting an output shows mixed types — workflows + models + voice — because the outcome, not the type, is the organizing unit. per-lane default: each lane pre-selects its dominant outputs.
**simulation:** kenji wants a video of himself talking for his channel. he taps `talking head` and gets 3 workflows, 2 video models, AND the voice model that completes the stack. he arrived wanting a result, and the grid handed him a recipe. no other filter on the site teaches the product thesis this fast.
**micro-criteria:** (1) ONE vocabulary file feeds outputs, intent chips (#42), lane subtitles — build set-check, drift = CI fail; (2) an output selection must be able to surface ≥2 entry types (proof it's outcome-organized, not a hidden type filter); (3) every entry declares ≥1 output (build assert — an entry with no output is uncategorizable and shouldn't ship).
**cost:** MEDIUM — same per-entry curation tax as #35, but this one is the owner's "organize by quality/use, not model brand" law operationalized. budget goes here FIRST.
**verdict:** ADOPT 9 — the product thesis as a control; this filter IS the differentiation from civitai's taxonomy.

### 37 — duration filter for image-to-video (MERGED into 36)
**restatement:** target-duration buckets (≤5s / 5-10s / 10s+) on video entries — render cost and ad slot lengths both scale with seconds.
**mechanism:** MERGED — not a bar occupant. duration is a sub-facet that appears (build-generated) inside output=video/reel contexts only, as a second chip row. curated `entry.duration` bucket on video-capable entries.
**simulation:** marcus needs a 15s client slot. he taps output `reel`, the duration row appears, taps `10s+` — the 5-second loop demos that wasted his morning are gone. the filter showed up exactly when it became relevant, which is also why it never clutters the persona lane.
**micro-criteria:** (1) duration on 100% of video-capable entries (build assert); (2) ≤4 buckets, ranges not seconds; (3) the row is ABSENT (not disabled) on tabs with zero video entries — no dead UI.
**cost:** small — curated field on a subset (video entries only).
**verdict:** MERGE with #36 — ADOPT 7 as a contextual facet; standalone it breaks the four-filter law (#31) for a niche need. the merge keeps the value, kills the clutter.

### 38 — audio-requirement filter for ad pipelines
**restatement:** chips for what a pipeline DEMANDS audio-wise (silent / narration / lip sync / music) — tells marcus what he's signing up for before import.
**mechanism:** curated `entry.audio[]` on Campaign Lab workflows; chips render in that lane only (lane-scoped filter, consistent with #37 pattern). selection also annotates the card dependency strip ("needs: voice model") so the filter and the preview (#78 dependency panel) never disagree.
**simulation:** marcus has no mic this week. he taps `silent` and sees pipelines shipping with music beds or text overlays only. the lip-sync monster he would have imported and abandoned never crosses his screen. the site understood that an ad pipeline's audio requirement is a commitment, not a detail.
**micro-criteria:** (1) audio field on 100% of ad-lane workflows (build assert); (2) ≤4 vocabulary values, shared const; (3) card dependency strip reflects the same audio fact as the chip — single data source, grep-verifiable.
**cost:** small-medium — per-workflow curation, but workflow count is dozens, not hundreds.
**verdict:** ADOPT 7 — real ad-planning value, lane-scoped so it costs nothing globally; synergy with audio-node role labeling (#83).

### 39 — consistency-lock filter (identity / clothing / product / scene)
**restatement:** the persona lane's killer filter — WHAT stays locked, because "consistency" is four different problems wearing one word.
**mechanism:** curated `entry.locks[]` with exactly 4 allowed values; chips in Persona Studio, inherited by the mature lane. the lock vocabulary is ALSO the anchor of the #41 synonym table ("same face" → identity lock), so search and filter converge on the same concept objects.
**simulation:** lia's daily pain: her character's face drifts between sets. she taps `identity lock` and the S-tier identity LoRAs and reference-face workflows surface — ranked within-lane per CRITERIA nsfw/persona normalization. someone categorized HER exact problem instead of "top models this week". that's the moment the site stops being a directory.
**micro-criteria:** (1) exactly 4 lock values, enum-enforced at build (no free tags); (2) every persona-lane entry declares ≥1 lock; (3) typing "same person" into search while this filter exists surfaces the same entries (search↔filter convergence test at build).
**cost:** MEDIUM curation tax on the flagship lane — worth it there, skip elsewhere.
**verdict:** ADOPT 8 — highest differentiation of the filter family; it names the lanes' actual jobs and becomes the synonym table's backbone.

### 40 — mature filtering kept separate from ordinary filters
**restatement:** mature is a LANE + gate (header toggle + confirmation), never a chip among type/VRAM chips — and once inside, the mature lane gets FULL filter parity.
**mechanism:** mature entries live in a separate lane view behind the header toggle (SFW default, blur mechanics per codex §5: blur 28px + solid overlay, click-to-reveal per entry only after lane unlock). inside the lane, the same four-filter bar (#31) operates on nsfw-normalized rankings (CRITERIA: nsfw ranked among nsfw only). no "nsfw" chip ever appears in the common bar — the lane IS the filter. global search excludes mature unless the lane is active.
**simulation:** lia unlocks the mature lane (one confirm, session-only), and inside it the filters are the SAME ones she learned in persona studio — VRAM, locks, type. nothing feels second-class, and nothing about her lane leaked into the SFW views her partner might open. respected in both directions.
**micro-criteria:** (1) SFW state exposes zero mature DOM — build greps rendered SFW output for mature names/urls/previews, any hit = CI fail; (2) filter parity: mature lane supports every filter the persona lane supports (build asserts same chip groups render); (3) toggle+confirm ≤2 clicks, resets to SFW per session unless 30-day opt-in explicitly checked; deep links `?lane=mature` still land SFW+confirm.
**cost:** low-medium — blur + normalization already decided in CRITERIA/codex doc; the discipline cost is keeping filter parity as new filters ship.
**verdict:** ADOPT 9 — safety law and parity law in one; separation IS the feature. note: task constraints (blurred previews allowed after toggle) override codex §5's blanket "no explicit imagery" — blur rules still apply verbatim.

### 41 — search understands outcome synonyms
**restatement:** build-time query expansion — a synonym table maps real human phrasings ("same person every image", "face consistency", "identity lock") into our controlled vocabulary before matching.
**mechanism:** python build emits `search-index.json`: for each vocabulary concept (locks, outputs, types), a list of ≥3 community phrasings (sourced from the reddit/community research file — not invented at a desk). client normalizes query → token-overlap match against expanded index → results + an ALWAYS-visible chip "we read this as: identity lock". exact-match on ourName/sourceName ranks above expansion hits.
**simulation:** kenji types "same person every image" — words, not taxonomy. the grid shows the identity-lock S-tier entries and one honest chip at the top: "we read this as: identity lock". he didn't have to learn our vocabulary; the site translated his. that translation moment is when a newbie bookmarks the site.
**micro-criteria:** (1) ≥3 phrasings per key concept, each traced to a community source URL in the research file (phrasings invented from a model's head violate "nothing from training dataset"); (2) interpretation chip renders on EVERY expanded query — silent re-ranking is banned (test: expanded query without chip = fail); (3) synonym table is data (JSON), adding a phrasing requires zero JS edits.
**cost:** MEDIUM — table authoring against community research; runtime trivial (precomputed index, in-memory scan). risk: over-expansion polluting results → mitigated by exact-first ranking + the interpretation chip making behavior visible.
**verdict:** ADOPT 9 — makes search speak human; converts the community-research investment into a UX asset; the vocabulary bridge for #39/#42.

### 42 — intent chips under search
**restatement:** four tappable intents (`new persona` / `product ad` / `talking video` / `voice`) under the search field — search for people who don't have words yet; each chip = one jump to a pre-filtered lane.
**mechanism:** 4 static buttons sharing the #36 vocabulary const; click routes to the lane with the matching output filter pre-applied via URL params (#10 state). zero typing required to enter the funnel.
**simulation:** marcus lands at 11pm, blank, no search terms in his head. the chips read like his todo list. `product ad` → Campaign Lab, pre-filtered, three S-tier pipelines. he never touched the keyboard and the site already knew why he came. the empty search box (the classic intimidation moment) never happened.
**micro-criteria:** (1) ≤4 chips, outcome phrasing only — no tech nouns ("LoRA" chip = instant fail); (2) every chip target is build-verified non-empty (≥3 entries) — a chip leading to zero results ships broken; (3) chips + search input never fight for space on mobile (chips wrap below input, no overlap).
**cost:** trivial — static links with query params.
**verdict:** ADOPT 9 — "enter through I need a result" (#5) made clickable; near-zero cost, onboarding-critical.

### 43 — command palette (⌘K)
**restatement:** keyboard-first overlay to jump to any entry, lane, or filter action without the mouse.
**mechanism:** `<dialog>` opened by cmd/ctrl+K (keydown listener), in-memory index (ourName, sourceName, creator, lane names, filter actions), subsequence fuzzy match, arrow nav, Enter routes, Esc closes. ~120 lines vanilla JS. visible `⌘K` hint in header.
**simulation:** the owner, 50th visit, keyboard in hand, audits the site: ⌘K, "soft-win", Enter — detail page. no scroll-hunting. it feels like a tool he'd keep open, not a page he visits. but marcus and kenji — the actual v1 audience — never press ⌘K in their lives; they'd have paid nothing for it and it shipped after their flows worked.
**micro-criteria:** (1) open ≤100ms, type-to-result ≤50ms at 500 entries; (2) full keyboard loop open→navigate→execute, Esc always closes, focus trapped in dialog; (3) hint visible in header (a secret palette doesn't exist).
**cost:** small-medium — ~120-150 lines + focus management edge cases; perf risk nil at this dataset size.
**verdict:** DEFER 6 — high craft, low v1 leverage: the audience (kenji/marcus/lia) is mouse-first, and search+chips+URL state already cover the fast paths. build in v1.1 as a power-user layer once core flows are proven. score = quality, not priority.

### 44 — explicit search scope (This lane / All lanes / Saved)
**restatement:** a three-way segmented control on search declaring WHERE the query hunts — results are never surprising, and Saved becomes searchable.
**mechanism:** segmented control (3 radio buttons styled as tabs) selects the dataset before query runs: current lane array / full array / localStorage shortlist ids (#70). scope persists per session; results header states it: "18 results in Persona Studio".
**simulation:** marcus saved six entries last tuesday. he types `voice` with scope `Saved` and his own shortlist filters down to the two voice-capable stacks. it's HIS library answering, not the storefront again. next keystroke he flips to `All lanes` to see what he's missing — one control, both worlds, zero surprise about which one he's in.
**micro-criteria:** (1) scope visible before AND after searching (label renders in the results line); (2) `Saved` with empty shortlist shows an onboarding hint ("nothing saved yet — bookmark cards") instead of a dead zero-results; (3) switching scope re-runs the query in place ≤50ms, no page nav.
**cost:** trivial.
**verdict:** ADOPT 8 — predictable search plus a second life for shortlists; cheap and load-bearing.

### 45 — three example queries in the empty search state
**restatement:** the empty search box teaches by example — three clickable sample queries, each verified at build to return good results.
**mechanism:** build picks 3 queries deterministically per lane (from the #41 synonym table, user-phrasing side), asserts ≥1 result each (CI-able), bakes them in. click = fill input + run search. examples double as vocabulary lessons — clicking shows the interpretation chip, teaching our language by demonstration.
**simulation:** kenji clicks the magnifier, sees a blank box — and under it, three plain-english queries. he clicks `same person every time` instead of freezing. results + the chip "we read this as: identity lock". in one click he learned both what the site has AND how to ask for it. the empty state went from wall to tutorial.
**micro-criteria:** (1) exactly 3, each build-verified non-empty (a broken example = CI fail, not a runtime surprise); (2) examples swap per lane (persona lane shows persona phrasings); (3) phrasings come from the synonym/user-language side, never the taxonomy side — the examples exist to bridge that exact gap.
**cost:** trivial (~30 lines).
**verdict:** ADOPT 9 — kills the dead empty state, showcases the synonym engine, teaches vocabulary; the cheapest high-value idea in this range.

### 46 — recent searches, local only
**restatement:** last five queries stored in localStorage under the search box, with an explicit stays-on-this-device promise — and a hard guard that mature-lane queries never surface in SFW mode.
**mechanism:** on submit, unshift into localStorage array (namespaced key, cap 5, dedupe), render as small chips with a clear-all control. static site = no network by construction; the privacy claim is architectural, not a policy promise.
**simulation:** lia searched `outfit lock` yesterday; today it's under the box, one tap. on her shared machine the mature-lane queries she ran never appear while SFW — the guard she didn't know she needed just worked. small feature, but it's the kind of small that decides whether she trusts the site with her actual workflow.
**micro-criteria:** (1) cap 5, oldest evicted, deduped — no unbounded list; (2) visible clear-all; (3) queries issued inside the mature lane are stored with a flag and NEVER rendered while SFW mode is active (leak test at build: render SFW with seeded mature history, assert absence).
**cost:** trivial — but the mature-history guard (#3) is the real content; ship it or ship nothing.
**verdict:** ADOPT 7 — modest QoL; the privacy framing and the mature-leak guard are what make it worth building.

### 47 — zero results → nearest outcome rescue
**restatement:** an empty result set is a redirect, not a wall: name WHICH filter caused the emptiness, offer the nearest non-empty concept and the cheapest filter relaxation, both one click, both guaranteed non-empty.
**mechanism:** on empty set, compute (a) nearest vocabulary concept by token overlap via the synonym index, (b) for each active filter, the result count if it alone were removed. render: "nothing matches `identity lock` at 6 GB — 5 entries open up at 8 GB or cloud" + button "show them". fallback: the three example queries (#45) always render below, so every empty state has ≥2 exits.
**simulation:** kenji, 6 GB laptop, types `identity lock` — zero. on any other site that's the end; here the page says his GPU is the blocker and offers the 8 GB-or-cloud entries in one click. he just learned the hardware landscape of his exact need without a forum trip. a dead end would have sent him back to reddit — this turned the worst moment of the visit into the most helpful one.
**micro-criteria:** (1) every rescue suggestion is COMPUTED (not canned copy) and clicking it always yields ≥1 result — a suggestion that 404s the grid = CI fail; (2) the causing filter is named explicitly (never "try different terms"); (3) ≥2 exits on every empty state (rescue + example queries).
**cost:** small — one pass over the in-memory set per active filter; trivial at this scale.
**verdict:** ADOPT 9 — "results visible" extended to its worst case; trust is built at the dead ends, and this is where competitors leave users stranded.

### 48 — search by creator name + original civitai name
**restatement:** alias indexing — our custom name stays primary, but the ORIGINAL creator/model name a user carries from a reddit thread resolves into our curated entry.
**mechanism:** build indexes `entry.creator` (API username, prefix-matched) and `entry.sourceName` (original model name) alongside `ourName`; hits show our name prominent with a secondary line "original: [name] by [creator]". exact hits on ourName outrank alias hits.
**simulation:** marcus read a reddit thread recommending "a flux lora by [creator]". he types the creator's handle — our entry appears, our name on top, provenance line under it. the site just positioned itself as the translation layer between community chatter and a curated, scored, importable library. that's the whole product in one search result.
**micro-criteria:** (1) creator + sourceName indexed for 100% of entries (build assert); (2) both names visible on alias hits — ours primary, never a silent redirect; (3) partial creator handle matches (prefix match) work.
**cost:** trivial — data already in the manifest for provenance (#92).
**verdict:** ADOPT 9 — closes the community-research loop end to end; near-zero cost, directly serves "our names everywhere, their names findable".

### 49 — freshness search + visible dates
**restatement:** freshness as both a filter (`updated <90d`) and a permanent per-entry fact (month-year date rendered), with labels honest about what `updatedAt` actually means.
**mechanism:** build computes age from version `updatedAt`; "updated this month" chip filters on it; every card/detail renders "version updated Aug 2026" (absolute date, not drifting relative). label says "version updated", never "improved" — CRITERIA caps freshness because updatedAt is creator-controlled (re-upload farming). stale entries (CRITERIA kill-lines) carry the visible `Needs re-test` state (#96) and sink in Latest sort only.
**simulation:** the owner opens the site before showing a friend. he taps `updated this month` and sees the current wave — z-image/turbo era entries near the top, a 2024 relic flagged and sinking. the site reads alive, not like a museum with fresh paint. and because labels say "version updated", nobody can accuse the site of mistaking a re-upload for progress.
**micro-criteria:** (1) absolute month-year on 100% of entries (never relative-only strings); (2) freshness filter and Proven sort never silently mix — they are explicit separate modes (#86); (3) label copy uses "version updated" verbatim (honesty cap from CRITERIA).
**cost:** trivial; data exists in the snapshot.
**verdict:** ADOPT 8 — REQUIREMENTS ("workflow age/recency visible") fulfilled with the honesty caveat built into the label; pairs with #86 sort modes.

### 50 — curated `Surprise me`
**restatement:** a dice action that draws ONLY from S/A tier, biased away from already-seen entries — serendipity with a curation guarantee, never a slot machine.
**mechanism:** JS random from `tier ∈ {S,A}` minus a capped localStorage seen-set; routes to the full detail view (never a bare image dump); `surprise again` button in place. pool composition asserted at build (an S/A-only pool that somehow contains C entries = CI fail).

**micro-criteria:** (1) pool = S/A only, build-asserted; (2) no immediate repeat draws (seen-set with a re-cycle window); (3) one click lands on the FULL detail view with context — never a preview-only dead end.
**cost:** trivial (~30 lines).
**verdict:** ADOPT 7 — cheap personality feature that showcases curation confidence; low priority vs core flows but it makes the library feel like a recommender, not a list.

## NEW ORIGINAL IDEAS (gaps found in 26-50 range)

### N1 — live chip counts (filter yield preview)
**gap:** ideas 31-39 make filters commit-then-see; nothing shows the consequence of a filter BEFORE or WHILE choosing. #47 rescues empty results after the fact; this makes emptiness visible in advance, on the chips themselves.
**restatement:** every filter chip permanently carries its live result count under the current filter state — `8 GB (41)`, `Flux (12)` — recomputed on every toggle, so the user reads the terrain before touching anything.
**mechanism:** each chip = `<button aria-pressed>` with two spans: label + count. one recomputation pass over the in-memory set after any toggle (500 entries × ~20 chips ≈ 10k predicate checks — trivial) using the SINGLE shared predicate function that also drives the grid (no drift between what the chip promises and what the grid renders). zero-yield chips get `disabled` + dimmed, never a clickable dead end. count swap animates via the #7 micro-interaction (colleague's table). counts are computed live, not baked, because they depend on active filter state.
**simulation:** marcus, 12 GB, opens Campaign Lab. before touching anything he sees `VRAM: ≤8 (9) · ≤12 (14) · cloud (21)` and `output: reel (11) · talking head (7)`. he taps `≤12` — instantly `Flux (5)` and `talking head (3)` update to reflect his hardware. he watched his own rig narrow the field in the numbers themselves, no dead-end clicks, no backtracking. when `reference face (0)` dims out he understands WHY his lane has none — the interface explained the terrain without a single error state.
**micro-criteria:** (1) counts correct under ANY filter combination — build-time property test: N random filter combos × assert chip count === brute-force count; (2) full chip-row recompute ≤50ms per toggle, no stale-number flicker (render after compute, single frame); (3) zero-yield chips `disabled` with count `0` visible — clickable-but-empty is a dead click and dead clicks are banned.
**cost:** trivial runtime; the discipline cost is keeping ONE predicate as single source of truth for grid + counts + rescue (#47) — three features, one function.
**verdict:** ADOPT 9 — makes the filter bar an honest map instead of a slot machine; prevents most #47 dead-ends from ever forming; embodies "better criteria for every small choice" at the exact smallest choice in the UI.

### N2 — named views (+N new diff)
**gap:** #10 shares view state via URL, #60 exports shortlists, #70 saves without an account — but nothing SAVES a lane+filter+sort combination as a personal recurring view, and nothing tells a repeat visitor what changed since their last visit.
**restatement:** "save this view" turns a filter combination into a named one-tap chip (`12 GB ad video`), and each stored view carries a `+N new` badge counting entries updated since the user last opened it.
**mechanism:** when non-default filters are active, a `Save this view` button stores `{name, lane, filters, sort, lastVisited}` in localStorage (cap 5, inline rename/delete). views render as a chip row under the lane nav; tap applies state through the same URL-sync mechanism as #10 (so views stay shareable). the `+N new` badge = count of entries in that view's filtered set with `entry.updatedAt > view.lastVisited` — the freshness data (#49) reused as a personal changelog. opening a view refreshes its watermark.
**simulation:** every monday marcus checks "what's new that runs on my 12 GB for ads". he built the view once: `≤12 GB` + output `reel` + sort `Latest`. this monday the chip reads `12 GB ad video +2` — two workflows updated since last week, one tap, sorted to the top. the library didn't just remember his routine; it told him what changed inside it. that +2 is the difference between a tool he visits and a tool he checks.
**micro-criteria:** (1) apply(view) → readState() === view (round-trip property test — restore is exact or the feature lies); (2) `+N new` computed only from `updatedAt` (never faked by re-render) and clears on open (watermark refresh); (3) cap 5 with visible inline management (rename/delete), oldest-view eviction never silent.
**cost:** small-medium — ~80 lines + state care; must compose with #10 URL sync (views are a layer over it, not a parallel mechanism — otherwise two state systems fight).
**verdict:** ADOPT 7 — turns repeat-visit rituals into first-class objects and reuses freshness data as a personal diff; the `+N new` hook is the original value. v1.1, not launch-blocking.
